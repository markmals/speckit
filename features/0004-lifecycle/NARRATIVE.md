# Narrative: The spec lifecycle

Specs are the durable library; implementations are regeneration targets. The lifecycle is the loop that keeps N native implementations honest against one spec, and it runs the same on every target: apply a spec to a target (failing tests first, then the minimum implementation, then verify to green and lock), and — when a target was edited directly and raced ahead of the spec — reconcile, folding that change back into the spec and the other targets.

Two things are deliberately disposable and two are deliberately durable. `plan.md` and `tasks.md` are per-(spec × target) disposable execution artifacts (D9): generated by `apply`, deleted or archived once the lock is green. The durable state is the **spec library**, the **lock** (what's verified green, by content hash), and the **ledger** (what each attempt cost and how it went). The task list is never the source of truth — drift and coverage are derived from the lock and reverse pointers, not from a checklist.

Reconciliation is never automatic. When a target leads, the engine *proposes* spec and cross-target updates; a human approves each diff. The agent does the typing; the human owns the direction.
